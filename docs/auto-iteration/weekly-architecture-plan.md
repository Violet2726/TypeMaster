## 2. 反复出现的问题

### 问题排序（按频率 × 严重程度）

| 排名 | 问题 | 频率 | 严重度 | 根因分类 |
|------|------|------|--------|----------|
| P1 | 缺少代码覆盖率监控 | 高 | 高 | 测试缺失 |
| P2 | practice-store.jsx 职责过重（444行） | 中 | 中 | 模块边界 |
| P3 | i18n 单文件臃肿（566行） | 中 | 中 | 数据结构 |
| P4 | 统一错误处理模式缺失 | 低 | 中 | 架构设计 |

### 详细分析

#### P1: 缺少代码覆盖率监控
- **位置**: CI/CD 配置
- **现象**: 已建立 171 个测试用例，但无覆盖率报告，无法发现测试遗漏
- **风险**: 新增代码可能缺少测试覆盖，无人值守合并时无法验证
- **修复价值**: 高（无人值守合并可靠性的关键）

#### P2: practice-store.jsx 职责过重
- **位置**: `src/store/practice-store.jsx`
- **现象**: 444 行，包含配置管理、AI 状态、教练状态、历史持久化、UI 联动
- **风险**: 新增状态时容易堆叠；测试困难
- **修复价值**: 中等

#### P3: i18n 单文件臃肿
- **位置**: `src/i18n/index.js`
- **现象**: 566 行单文件，中英文文案硬编码在同一对象中
- **风险**: 新增文案时容易只改一处导致不同步；大型文件维护困难
- **修复价值**: 中等（长期可维护性）

#### P4: 统一错误处理模式缺失
- **位置**: 分散在各模块
- **现象**: 错误处理无统一模式，各模块自行处理
- **风险**: 可维护性差，错误追踪困难
- **修复价值**: 中等（可延后）

## 4. 下周最多三个重构主题

### 主题 A: 代码覆盖率监控集成

#### 目标
集成 Vitest 覆盖率报告到 CI/CD，确保所有关键模块有足够的测试覆盖。

#### 涉及模块
- `vitest.config.js`
- `.github/workflows/ci.yml`
- `package.json`

#### 为什么必须重构
- 已有 171 个测试用例，但无覆盖率报告，无法发现测试遗漏
- 无人值守合并时需要量化验证测试覆盖情况
- 这是提升无人值守合并可靠性的关键基础设施

#### 旧逻辑清理范围
- 不改动任何业务逻辑
- 仅配置覆盖率收集和报告

#### 验收标准
- `npm run test:coverage` 生成覆盖率报告
- CI/CD 流程中包含覆盖率检查
- 关键模块（engine、services）覆盖率 ≥ 80%
- `npm run build` 通过
- `npm test` 通过

#### 风险
- 低风险：纯配置修改，不改变业务逻辑

#### 不做什么
- 不改动测试用例
- 不引入新的测试框架
- 不强制 100% 覆盖率

## 6. 自动化测试补强建议

### 最能提升无人值守合并可靠性的测试

#### 优先级 1: 代码覆盖率监控（本周主题 A）
- **原因**: 已有 171 个测试，但无法量化覆盖范围
- **预期收益**: 防止新增代码缺少测试覆盖
- **影响范围**: 覆盖所有模块

#### 优先级 2: practice-store.jsx 拆分（长期）
- **原因**: 当前 store 职责过重，难以测试
- **预期收益**: 提升可维护性和可测试性
- **方案**: 主题 B 验证后实施拆分

### 测试策略原则

1. **engine 模块**: 纯函数优先，已有良好测试基线（117 tests）
2. **services 模块**: 依赖外部资源，需要 mock（storage.js 和 ai-service.js 测试已建立）
3. **store 模块**: 组合逻辑，可通过 engine + services 测试间接覆盖
4. **components 模块**: 渲染测试 ROI 低，优先保证下层测试
